## 중단 후 복구되지 않은 이유

현재 코드의 timeout 분기는 `stop_drive_control()`을 호출하고 `TimeoutError`를
발생시킨다. Expert stop은 SIGTERM을 전송한다. main_runner의 auto_repeat는
`scenario.run()`이 정상 반환한 뒤에만 실행되며, TimeoutError를 처리하는
재시도 분기가 없어 timeout이면 다음 시나리오로 넘어가지 않는다.

Sync Runtime은 fresh 제어 상실 후에도 failsafe 제동으로 tick과 capture를
계속한다. manifest에는 fresh 1,793개, reused 4개, failsafe 20,489개가 있다
(최초 시작 시 failsafe 1개 포함). 이는 이미지 파일 수나 정상 데이터셋으로
최종 변환된 샘플 수가 아니라 manifest 레코드 수다.
frame 9101에서 속도는 약 0.004km/h였고, 마지막 frame 111426에서도
같은 위치에서 약 0.003km/h로 정지 상태였다.

## 남은 한계와 수정 방향

- 당시 Runner stdout/stderr의 TimeoutError 원문이 없어 SIGTERM 발신 원인에
  대한 직접 증거는 없지만, 시간·궤적·종료 순서·현재 코드가 서로 일치한다.
- 현재 코드를 이용한 재생이며 당시 실행 코드/설정의 완전한 스냅샷은 아니다.
- Windows의 이후 블루스크린은 별도 사건이며 06:37의 Expert 종료와 구분한다.
- 15분이 시뮬레이션 주행 시간 요구라면 주행 제한을 Sync frame 시간 기준으로
  계산해야 한다. 실제 15분 요구라면 그 제한 자체는 현 동작과 일치하며,
  처리 속도/주행 조건 개선 또는 제한 시간 재검토가 필요하다.
- 장시간 수집에는 Runner 오류의 영구 로그와 수집 측 실패 상태 전파가 필요하다.
  제어 종료 후 정지 프레임을 계속 정상 수집으로 취급하면 같은 문제가 반복된다.

이번 조사에서는 실행 코드와 설정을 변경하지 않았다.
