# 데이터 노출·데이터 부족·정보 활용의 분리 진단

2026-09-11. 기존 9,540-update 모델과 최근 320-update pilot을 구분한 train 중심 분석입니다. Validation 성능은 보고하지 않습니다. 원본 데이터·production 코드·기존 모델 가중치를 바꾸거나 후속 학습을 시작하지 않았습니다. 새 진단 파일과 보고서만 추가했습니다.

## 핵심 결론

현재 문제를 **“전체적인 주행 방식은 맞고, 데이터가 적어서 정확도만 조금 떨어지는 상태”**로 설명하면 부정확합니다.

1. **전체 대회 경로를 외우려는 목표에는 실제 학습 범위가 부족합니다.** 시간순 앞 약 80%가 수집한 주행거리의 약 42%에 불과합니다. 뒤쪽 도로의 상당 부분을 학습에서 제외한 상태입니다.
2. **이미 학습한 회전·출발 장면의 실패는 데이터 미투입만으로 설명되지 않습니다.** 기존 장기 학습은 배정된 train 프레임의 약 98%를 실제로 사용했고, 명시적 회전 및 첫 초록불 장면도 반복 감독했습니다.
3. **장기 학습 모델은 이동 길이보다 방향 조건 학습에 문제가 남았습니다.** 이동거리 비율은 실제와 가까워졌지만 좌회전 34개 모두 반대 부호의 좌우 변위를 출력했습니다. 단순한 작은 위치 오차가 아닙니다.
4. **신호등 출발에는 입력 표현 문제의 구체적인 근거가 있습니다.** 원본 사진에 초록불 전환이 찍혀 있는데, 축소 후 단서가 작고 frozen token의 변화가 평소 정지 장면 변동 수준입니다.
5. **데이터 양의 효과와 최적화의 효과는 아직 완전히 분리되지 않았습니다.** 새 데이터 없이 같은 최종 특징에서 더 낮은 train-anchor 오차를 얻는 수치적 readout 해는 있지만, 이것이 원래 모든 프레임의 학습 목적이나 새로운 상황의 주행 성공을 보장하지 않습니다.

따라서 다음 우선순위는 무조건 재수집하거나 논문 구조를 바꾸는 것이 아니라, **경로 학습 범위, 희소한 회전·출발 사건의 노출, 신호 단서의 입력 품질, 현재 모델의 train-fit 능력을 분리해 확인하는 것**입니다.

## 1. '시간 80%'가 '도로 80%'는 아니었음

원본 ego 위치와 route 진행도를 다시 계산했습니다.

| 범위 | 시뮬레이션 경과시간 | 실제 주행거리 | 실제 움직인 시간, speed ≥ 0.1m/s |
| --- | ---: | ---: | ---: |
| 전체 수집 4,240프레임 | 423.9초 | 2,175.01m | 약 213.0초 |
| Train에 배정된 앞 3,352프레임 | 335.1초 | 922.96m | 약 124.2초 |

앞부분에는 약 211초의 신호 대기가 있고, 뒤쪽 약 89초는 계속 이동한 구간입니다. 따라서 시간 기준 train 배정은 약 79.1%지만 실제 주행거리 기준으로는 **42.43%**입니다. 나머지 약 1,252m는 train 입력 범위 밖입니다. 이 수치는 validation의 예측 성능이 아니라 데이터 사용 범위입니다.

전체 수집은 route link index 0–38을 지나지만 실제 선택된 downstream supervision의 마지막 입력 frame3345는 link22, 약 918.27m 지점입니다. Train 배정의 마지막 frame3351은 link23입니다. 전체 기록의 끝까지 모델이 학습했다고 볼 수 없습니다.

여기서 918.27m는 실제 supervision의 처음부터 마지막까지 도달 범위이지, 빠진 중간 프레임이 전혀 없다는 뜻은 아닙니다. 미래 GT가 현재 위치보다 약간 앞까지 포함하는 것과 그 도로의 센서 입력을 학습한 것도 구분해야 합니다.

**전체 경로를 overfit하려는 목표와 현재 시간순 분할이 충돌합니다.** 나머지 도로 데이터는 이미 수집되어 있으므로, 이 문제 자체는 반드시 재수집해야 해결되는 문제가 아닙니다. 다만 기존에 정한 train/validation 분할을 변경하는 것은 별도의 결정이며 이번 진단에서는 바꾸지 않았습니다.

## 2. Train으로 배정한 데이터가 loader에서 대량 누락됐나? — 아니었음

기존 장기 학습의 실제 로그와 window 구성을 재구성했습니다.

- 선택된 636개 anchor가 매 epoch마다 정확히 1회씩, 총 15회 사용됐습니다.
- 3,352개 train 프레임 중 실제 고유 supervision 프레임은 3,282개, 약 97.9%입니다.
- 겹치는 11-frame window 때문에 고유 프레임별 감독 횟수는 15–45회였습니다.
- 우회전 지시 구간 60프레임 중 56프레임, 좌회전 지시 구간 52프레임 중 46프레임이 학습됐습니다.
- 우회전 지시의 전체 loss 적용 횟수는 1,650회, 좌회전은 1,320회였습니다. 새 독립 주행 사건 수가 아니라 반복 및 window 겹침을 포함한 횟수입니다.
- 첫 초록불 frame991/1591/2491/2791도 각각 30회씩 loss에 들어갔습니다. 마지막 anchor가 아니어도 clip 내부 프레임으로 감독됩니다.
- Cache의 3,352개 미래 GT는 실제 미래 ego 좌표와 일치했고, 입력과 정답의 순서/해시 계약에서도 대량 누락·뒤섞임을 확인하지 못했습니다.

반면 최근 pilot은 **32개 window, 345개 고유 supervision 프레임**만 사용했습니다. 첫 초록불 네 장면은 pilot에서 빠졌습니다. 그러므로 최근 320-update의 큰 이동거리 오차를 전체 데이터 학습이 끝난 결과처럼 해석하면 안 됩니다.

이 두 실험의 사실은 모순이 아닙니다. 기존 장기 학습에는 장면이 들어갔고, 최근 작은 비교 실험에는 일부가 빠졌습니다.

## 3. 장기 학습 모델은 '기조는 맞고 정확도만 부족'한가?

### 전진 길이는 상당히 배웠지만 회전 방향은 그렇지 않음

기존 장기 학습의 636개 train anchor 중 이동 표본은 220개입니다. 이들의 `예측 종점 변위 / 실제 종점 변위` 중앙값은 **97.37%**였습니다. 최근 320 pilot의 약 28–47%와 다르게, 오래 학습한 모델은 이동 길이를 상당히 맞췄습니다. 표본 구성이 다른 수치이므로 순수한 학습량 효과의 A/B 비교는 아닙니다.

하지만 실제 미래 좌우 변위가 2m 이상인 곡선 81개에서는:

- 실제 마지막 좌우 변위 절댓값 평균: **4.08m**.
- 예측 마지막 좌우 변위 절댓값 평균: **0.43m**.
- 곡선 FDE: **4.18m**.
- 종점 제곱오차 합의 **90.78%가 횡방향**입니다.
- 좌곡선 34개 모두 예측 좌우 변위가 음수, 즉 정답인 왼쪽의 반대 방향이었습니다.
- 명시적 우회전 지시 10개도 예측 회전 폭이 모두 0.5m 미만이었습니다.

따라서 **“차는 적당히 전진하지만 회전 경로를 거의 직선으로 만드는 문제”**가 남았습니다. 이미 본 좌/우 지시를 제대로 구별하지 못하는 것으로, 단순한 약간의 위치 정확도 부족과 다릅니다.

참고로 직전 보고서에서 320 pilot의 큰 오차는 주로 전진 길이였습니다. 여기서는 9,540-update 모델을 분석하므로 지배적인 오차 방향이 달라집니다. 곡선의 기준도 이번 표는 최종 좌우 변위 2m 이상으로 통일했으며, 예전 1m 기준 100개 표와 직접 혼합하지 않습니다.

### 기존 평균 점수가 좋아 보인 이유

636개 중 416개는 정지 표본이고 거의 정확히 정지로 예측했습니다. 전체 ADE/FDE는 0.421/0.935m지만, 이동 220개만 보면 1.206/2.690m입니다. 전체 평균 하나만 보면 회전 문제가 가려집니다.

## 4. 새 데이터가 없으면 이미 본 정답조차 더 잘 맞출 수 없나?

기존 모델을 가중치 변경 없이 GPU로 실행해 636개 anchor의 중간 표현을 추출했습니다. 당시 RoPE 계산을 진단 프로세스 안에서만 재현했고, **636개 저장 예측과 모두 정확히 일치**했습니다. 검사 전후 trainable/frozen hash도 같았습니다.

그 뒤 NumPy로만, 같은 특징과 기존 정답 사이의 선형 회귀 계수를 직접 계산했습니다. 실제 모델의 optimizer를 실행하거나 계산한 계수를 모델에 반영하지 않았습니다.

동일한 최종 MLP의 ReLU 특징에 대해 `2048 → 10` 선형 readout을 계산한 예:

| 같은 636개 train anchor | ADE | FDE | 곡선 81개 FDE |
| --- | ---: | ---: | ---: |
| 기존 학습 모델 | 0.421m | 0.935m | 4.183m |
| 진단용 직접계산 readout, ridge λ=1e-8, CPU BF16 계산 | 0.176m | 0.337m | 0.547m |

이 진단 해에서는 좌곡선 34개와 우곡선 47개 모두 올바른 부호와 0.5m 이상의 회전 폭을 냈습니다. Anchor의 L1도 0.2458m에서 0.1052m로 줄었습니다. FP64에서는 FDE 0.312m였으며, 위 표는 실제 CPU BF16 선형 연산으로 수치적 실현 가능성을 추가 확인한 결과입니다. GPU bitwise 동일성이나 학습 안정성을 검증한 것은 아닙니다.

이는 **같은 데이터와 같은 최종 특징을 이용해, 이 train anchor들에서 더 낮은 오차를 내는 선형 함수가 존재한다**는 뜻입니다. 데이터가 없어서 이 정답을 표현하는 것이 원천적으로 불가능하다는 설명과는 맞지 않습니다.

다만 다음 한계를 반드시 유지해야 합니다.

- 원래 학습은 11개 프레임 모두를 감독하지만 이 계산은 636개 마지막 anchor만 대상으로 합니다. 원래 전체 학습 목적을 더 낮춘다는 증거는 아닙니다.
- 직접 계산은 제곱오차 기반이며 원래 waypoint loss는 L1입니다. 이 비교가 회귀 head 교체를 권고하는 것은 아닙니다.
- 약한 ridge는 미세한 특징 차이를 증폭할 수 있습니다. 이 해의 계수 L2 norm은 약 164.73이며 BF16과 FP64 사이 최대 좌표 차이는 약 0.497m였습니다. 수치 민감성을 가진 진단 해이지 안정적으로 배포할 해라고 판단하지 않습니다.
- 특징 차원이 표본 수보다 크므로 단순 암기가 가능합니다. 무작위 특징 대조군도 같은 표본에서는 거의 0 오차로 암기했습니다.
- 구간을 분리한 readout 검사에서는 회전 정보의 재사용이 약했습니다. 따라서 새로운 상황이나 전체 경로에서의 성능은 보장하지 않습니다.
- Encoder와 LLM은 이 train 데이터를 이미 학습했습니다. 아래 '구간 분리'는 진단용 readout 계수 계산 구간만 분리한 것이며 진짜 독립 validation이 아닙니다.

## 5. Vision token에 어떤 정보가 있고 어떤 단서가 약한가?

669개 train 내부 anchor에 대해 회귀 계수 계산용 구간과 평가 구간을 네 묶음으로 나누고, history/GT가 겹치지 않게 35프레임을 제외했습니다. Ridge λ=0.01을 사전 고정한 결과, waypoint token에서:

- 현재 speed를 읽는 오차: **0.47m/s**, 상수 예측 기준 3.84m/s.
- 미래에 움직이는지의 균형 정확도: **96.52%**, 상수 기준 50%.
- 곡선의 마지막 좌우 오차: 약 **3.95m**.

속도·정지 정보가 전부 사라진 것은 아닙니다. 반면 회전 형상을 다른 구간에서도 쉽게 읽을 수 있는 표현은 약했습니다. 전체 106 token이나 단순 history 차이를 사용해도 이 회전 문제가 크게 없어지지 않았습니다.

그렇다고 frozen encoder에 회전 정보가 전혀 없다고 단정할 수는 없습니다. 한 번만 지나간 회전 구간을 계수 계산에서 제외하면 그 장소의 유일한 사례도 빠지고, 이 feature-only 검사에는 navigation instruction도 없습니다. **데이터 다양성, 경로 문맥, 특징의 읽기 어려움이 섞여 있는 결과**입니다.

근거: [Frozen feature 분석](outputs/diagnosis_data_sufficiency_20260911/features_report.md).

## 6. 출발 실패: 원본에는 초록불이 보였음

원본 front 사진 두 쌍을 직접 확인했습니다.

- frame990 → 991: 전방 머리 위 신호가 빨강에서 초록으로 변합니다.
- frame2490 → 2491: 전방 신호가 빨강에서 초록 및 좌회전 허용 표시로 변합니다.

해당 경계의 gRPC 상태도 각각 1→16, 1→48로 바뀌고 frame 내부 tick은 정합합니다. 따라서 **이 두 사례를 카메라 미수집, 동일 이미지 반복 저장, 신호가 시야에 없음으로 설명할 수 없습니다.** 모든 신호의 3D ID 매칭이나 모든 프레임을 검증한 것은 아닙니다.

### 전처리에서 단서가 매우 작아짐

현재 front 전처리는 1280×720 → 341×256 resize 후 224×224 중앙 crop입니다.

- 검사한 신호등은 main-front crop 안에 남습니다.
- 하지만 원본 등불 bounding box를 resize 비율로 환산하면 약 **가로 2–3, 세로 3–4픽셀**입니다. 실제 resize 결과의 색 픽셀을 센 값이 아니라 기하학적 환산입니다.
- 별도 `rgb_center` 입력은 원본 중심 128×128 crop이며, 이 두 머리 위 신호등은 그 영역 밖입니다. 이 신호등을 확대해 제공하는 입력이 아닙니다.
- 16:9 원본을 341×256으로 강제 변환하므로 종횡비도 보존되지 않습니다. 이 변형의 성능 영향은 별도 실험 전에는 확정할 수 없습니다.

### 첫 초록불과 움직이기 시작한 뒤의 특징 변화가 다름

첫 초록불 4개 지점은 3초 전 빨간불 때와 ego 위치가 같고 speed도 거의 0입니다. 실제 미래 종점은 0에서 약 **4.15–11.11m 전진**으로 달라지지만, waypoint token의 상대 변화는 **2.8–3.6%**로 정지 중 평소 변동 범위 안이었습니다. 실제 움직임이 시작된 +3프레임에는 약 13–85%로 커집니다.

기존 encoder의 traffic head도 첫 초록불 네 장면을 모두 red로 분류했습니다. 이 head의 이산 예측이 그대로 downstream에 입력되는 것은 아니지만, 작은 신호 변화의 표현·판독이 약하다는 근거입니다.

다만 작은 L2 차이가 곧 정보 부재를 증명하는 것은 아니고, 단순 speed-only 지름길이라고 확정해서도 안 됩니다. 이전 속도만 바꾼 진단에서도 초록불 이후 scene의 움직임 예측이 완전히 사라지지는 않았습니다.

## 7. '데이터에 있는 정보'와 '모델이 받는 정보'도 다름

현재 입력은 센서와 현재 speed로 만든 frozen visual token, 그리고 주행 지시문입니다. Speed는 token 생성에 반영되며 누락되지 않았습니다.

하지만 숫자로 된 global path 전체, local target point, 정지선 거리, 다음 회전까지 거리를 LLM에 직접 전달하지는 않습니다. Global-path target point는 VE의 waypoint prediction head에서 사용되지만, feature-return branch에서는 사용되지 않습니다. 기존 v1 instruction은 현재 link 명령을 짧은 문장으로 변환합니다.

따라서 더 풍부한 경로 정보를 사용하는 expert의 출력을, 모델은 센서 특징과 짧은 지시로 다시 추론해야 합니다. 이것은 명백한 loader 버그가 아니라 현재 입력 설계의 제약입니다. 주어진 경로를 외우려는 목표에서 충분한 경로 문맥을 지시문에 제공했는지는 검토해야 하지만, 이것 하나로 이미 학습한 좌회전 실패까지 설명되지는 않습니다.

근거: [입력 계약 감사](outputs/diagnosis_data_sufficiency_20260911/input_contract_audit.md).

## 8. 이전 loss 불균형 설명의 적용 범위를 바로잡음

최근 320 pilot에서는 reconstruction gradient가 selector를 압도한다는 실제 측정이 있습니다. 그러나 이를 기존 9,540-update 모델의 말기 주행 실패에 그대로 적용하면 안 됩니다.

기존 장기 학습에서는 reconstruction loss가 마지막으로 0이 아니었던 update가 **2,572**였습니다. 이후 **6,968 update는 reconstruction=0**입니다. 토큰을 전부 남겨 복원 대상이 사라졌기 때문입니다. Epoch15의 gradient norm 중앙값은 3.24이고, clipping 상한 10을 넘은 것은 636회 중 196회였습니다.

전체 중앙값은 정지 표본의 비중에 영향을 받습니다. 이동 220개에서는 196개가 clipping됐고 norm 중앙값은 약 19.83, 곡선 81개는 전부 clipping됐고 중앙값은 약 21.70이었습니다. 따라서 '말기에는 최적화 제한이 전혀 없었다'는 주장도 틀립니다. 이 로그는 전체 norm이므로 횡방향 gradient만 막혔다는 증거는 아닙니다. Clipping 배율을 AdamW의 최종 parameter update 배율로 동일시하지 않습니다.

주의: **reconstruction loss 값이 0이라는 사실만으로 reconstruction gradient까지 0이라고 결론낼 수 없습니다.** 현재 ST mask에는 `d[(1-M)E]/dM=-E`라는 직접 미분 경로가 남습니다. 따라서 scalar 로그만으로 말기 reconstruction의 상대적 gradient 크기를 판단했던 설명은 충분하지 않았습니다.

후속 직접 측정에서는 원본 최종 가중치, 원래 11-frame 입력, training/Gumbel 모드에서 frame585/2865/2970을 검사했습니다. 주행 loss의 전체 gradient norm은 각각 2.789/19.196/19.663, 복원 loss의 전체 gradient norm은 0.00408/0.00876/0.01000이었습니다. 복원 gradient는 selector와 그 입력 정규화에만 남았고, MEFA/Q-Former/LLM/waypoint head의 복원 gradient는 0이었습니다. 토큰을 줄이려는 selector gradient도 약 1.6e-6~6.3e-6으로 매우 작았습니다.

그러므로 **검사한 최종 모델의 세 입력에서는 복원 gradient가 전체 주행 학습을 압도하지 않았습니다.** 이는 6,968개 과거 step 전체의 gradient를 재생한 결과가 아닙니다. 초기 압축 정책 형성에 영향을 줬을 가능성과, 그 뒤 남은 회전 학습 문제는 구분해야 합니다. 근거: [최종 모델의 loss별 gradient 실측](outputs/diagnosis_data_sufficiency_20260911/final_objective_gradients.json). 기존 예측 재현과 가중치/production source 불변을 검증했으며 optimizer update는 0입니다.

말기 waypoint L1은 epoch14→15에 약 1.38% 더 줄었고 곡선 clip의 감소는 약 0.89%였습니다. 완전한 수렴이나 영구적 plateau를 증명하지는 않습니다. 다만 LR가 schedule 끝에서 거의 0이 되어 단순히 같은 종료 상태를 이어 돌리면 충분하다고 판단할 근거도 없습니다. 매 epoch의 train ADE/FDE는 저장되지 않아 방향별 수렴 곡선까지 복원할 수는 없습니다.

## 9. 데이터가 부족하다는 말의 정확한 의미

| 질문 | 이번 진단의 판단 |
| --- | --- |
| Train loader가 데이터를 대량 누락했나? | 기존 장기 학습에서는 아님. 배정된 train 프레임 약 98%가 반복 감독됨. |
| 전체 대회 경로가 학습됐나? | 아님. 시간순 분할 탓에 실제 주행거리 약 42%만 train 범위에 있음. |
| 최근 320 pilot이 충분한 전체 학습인가? | 아님. 32개 window만 사용한 초기 비교 실험임. |
| 이미 본 회전이 작은 오차만 내나? | 아님. 장기 모델도 좌회전 부호와 회전 폭에 체계적인 실패가 있음. |
| 독립적인 주행 사건 수는 충분한가? | 제한적임. 명시적 좌/우 maneuver 각 1회, 주요 첫 초록불 4회 등 반복성이 낮음. 프레임 반복은 새 사건이 아님. |
| 새 데이터를 많이 모으면 지금 문제가 해결되나? | 미확정. 경로 범위는 넓힐 수 있으나 작은 신호 단서와 기존 표본의 정보 활용 문제는 별도로 남을 수 있음. |
| 논문 구조를 바꿔야만 하나? | 입증되지 않음. 입력·표본·수치적 학습 가능성의 분리 검사가 먼저임. |

현재 필요한 검증은 같은 논문 방향을 유지한 채, **기존의 명확한 좌/우/출발 표본을 충분히 맞출 수 있는지** 확인하는 작은 통제 실험입니다. 그 전에는 데이터량만 늘리거나 구조 수정만 반복하는 방식으로 원인을 특정하기 어렵습니다. 전체 경로 overfit용 데이터 사용 범위와 독립 검증 범위도 목적에 맞게 별도로 결정해야 합니다.
