# 실시간 입력 지연 재수정 및 실제 GPU 검증 — 2026-09-25

## 문제와 변경

**최종 채택: 최대 2프레임 VE batch + pinned/비동기 입력 전달 + 기존 약 2초 이력.** 중간에 시험했던 2.4초 시간 범위 완화는 정확도 저하가 관찰되어 기본 설정에서 철회했다. 아래의 2.4초 결과는 비교 실험이며 최종 설정이 아니다.

최종 실제 UDP 시험은 **2.295Hz(초기 준비 포함), 센서→출력 중앙값 594ms**였다. 같은 MORAI 환경의 수정 전 측정은 **1.057Hz, 778ms**였다. 아래 최종 측정 절에 원본 로그, 시각/이력 검증, 제한을 기록했다.

앞선 입력 변경에는 두 문제가 있었다. 처음의 raw-window 방식은 새 window마다 11개를 거의 모두 인코딩했다. 이를 프레임별 VE와 특징 캐시로 바꾼 다음에는, slot 하나가 빠질 때도 캐시 전체를 비워 다시 연속 11개를 기다렸다. MORAI와 GPU를 공유할 때 VE가 200ms를 넘으면서 후자의 문제가 실제로 발생했다.

이번 변경은 UDP 수신·CPU 전처리·VE·Stage2를 분리한 구조를 유지하며 다음을 고친다.

- 실제 수신 시각과 ID를 가진 최근 특징 11개를 재사용한다. 짧은 slot 누락만으로 캐시 전체를 지우지 않는다.
- 11개 특징의 실제 시간 범위는 최대 **2.12초**, 인접 실제 프레임 간격은 최대 **0.32초**로 제한한다. 목표 간격은 고정 0.2초이다. 개별 grid 시각 허용 오차는 실제 수신 로그에 근거해 ±0.06초에서 **±0.07초**로 바꿨다. 전체 span 상한은 늘리지 않았다. 오래된 특징은 제거하고 큰 단절 또는 generation 변경은 새 이력을 요구한다.
- VE가 실제 입력을 최대 2장씩 계산하고, 각각의 특징·시각·ID·navigation을 원래 프레임에 연결한다. LLM 입력은 계속 11프레임이다. 묶음 대기는 최대 0.22초이며, 한 장만 있으면 한 장만 계산한다.
- CPU 전처리 결과를 제한된 수의 pinned 메모리에 준비하고 비동기로 GPU에 전달한다. PointPillars에서 Python slice 길이로만 쓰는 `num_points`는 CPU에 둔다.
- 완료한 최신 window만 Stage2에 넘기며 이전 window를 FIFO로 쌓지 않는다. VE 시작 시 가장 최신 입력의 실제 나이는 0.3초 이하이다. 2장 묶음의 앞 프레임만 한 grid 간격만큼 더 오래될 수 있어 최대 0.5초이며, 이를 실제로 최신 프레임인 것처럼 표시하지 않는다. 출력 유효시간 검사는 유지한다.
- `history_temporally_extended`, 실제 span/평균 간격, 인접 간격, 특징 이력 reset/시간 범위 거부 횟수를 기록한다.

### 검토 후 철회한 시간 범위 확대

학습 입력은 11개, 간격 약 0.2초, 전체 약 2초이다. 이전 고정 grid의 실제 span 허용 범위는 약 1.88~2.12초였다. 먼저 누락 시 최대 2.4초까지 허용하는 정책을 시험했다. 모델에는 실제 timestamp가 입력되지 않아 이 차이를 자체 보정한다고 볼 수 없다. 원본 시각을 바꾸거나 프레임을 복제·보간하지는 않았지만, 시간 간격 자체가 바뀌어 정확도 저하가 확인됐다. 따라서 최종 설정은 2.12초로 되돌렸다.

학습·추론 모델 가중치, FP32 VE, FP16 캐시 양자화 경계, Gumbel 선택, velocity=0 recipe, 제어기는 변경하지 않았다. batch별 GPU 연산의 미세한 수치 차이는 기존 cache 허용 오차 안에서 검증했다.

## GPU 입력 전달 수치 검증

실제 UDP에서 받은 3개 입력에 대해 기존 blocking copy와 pinned/non-blocking copy를 비교했다. GPU에 전달된 센서 tensor 값은 모두 완전히 같았다. `num_points`도 CPU/GPU 위치만 달라졌으며 값은 같았다.

VE 출력은 bit 단위로 같지는 않았다. 변경 전 방식을 같은 입력에 반복 실행해도 최대 절대 차이가 0.0009765625~0.001953125 발생했고, 변경 방식과의 최대 차이도 같은 범위였다. RMSE는 약 0.000080~0.000084였다. 기존 cache 검증 기준 `atol=0.002, rtol=0.002`는 세 입력 모두 통과했다. 이를 완전한 bit 재현성으로 표현하지 않는다.

첫 parity 시도는 완전 일치 조건 때문에 중단했다. 이후 기존 방식 자체의 반복 실행 차이까지 함께 측정해 위 결과를 확인했다. 수치 커널/모델은 변경하지 않았다.

pinned 입력 한 개는 2,028,548바이트(약 1.93MiB)이다. 최종 설정의 대기 queue와 VE batch는 각각 최대 2개, 특징 캐시는 11개이다. batch 결합용 CPU 버퍼도 소량 추가되며, raw FIFO나 대용량 batch를 늘리는 방법은 사용하지 않았다.

## 2초 이력 + 2장 VE 전체 UDP 시험

`outputs/inference/vldrive_20260925_001933_399117/`에서 60초 실제 실행했다. 117개 출력, 초기 준비 포함 1.944Hz, 첫 출력 이후 2.240Hz였다. 센서→출력 지연 중앙값 607ms/P95 917ms, 출력 간격 중앙값 0.382초/P95 0.500초/최대 2.765초였다.

실제 11프레임 span 중앙값 2.002초/최대 2.102초, 인접 간격 최대 0.270초였다. 시간 범위를 넓힌 출력은 0개였다. VE는 146batch로 292프레임을 처리했고, 대기 queue drop은 2회였다. 센서 grid 누락 5회와 특징 이력 reset 6회가 남아 있어 모든 공백이 제거된 것은 아니다.

이 실행에서 묶음의 앞 프레임도 일시적으로 발행되어 LLM이 이를 가져가는 경우를 발견했다. 최종 코드는 2장 처리가 모두 끝난 뒤 **마지막 프레임을 anchor로 삼은 window만 한 번 발행**한다. 따라서 한 batch를 두 번 추론하지 않는다.

이후 `vldrive_20260925_002430_527057` 반복 실행은 출력 72개/1.200Hz로 다시 불안정해졌다. 이를 성공 결과에서 제외하지 않고 원인을 확인했다. 실제 수신 log의 299개 grid 목표 중 16개에서 가장 가까운 원본 시각이 60.6~66.1ms 떨어져 있었다. 기존 허용 오차 60ms보다 불과 0.6~6.1ms 커서 이를 누락으로 처리했으며, 연속 이력을 재준비하느라 수 초씩 출력이 끊겼다. 수신 자체가 없는 사례가 아니었다.

이 때문에 개별 grid의 시각 허용 오차를 70ms로 조정했다. 해당 log에서는 70ms를 넘는 nearest sample이 없었다. 전체 11개 이력의 span 상한 2.12초와 인접 간격 상한 0.32초는 유지한다. 개별 프레임 허용 오차가 10ms 넓어진 것이므로 학습 시각과 완전히 같은 입력이라고 표현하지 않는다. 이론적 짧은 쪽 span은 1.86초까지 가능하지만 2.4초로 긴 이력을 사용하는 정책과는 다르다. 실제 시각을 바꾸거나 missing frame을 만들지 않는다.

- grid 누락/만료 0회, VE 시작 stale 0회, 시간 범위 거부 0회. queue drop 5회, 특징 이력 reset 1회, 입력 거부 6회, 계산 후 예측 폐기 1회는 남았다. 패킷 손실이나 모든 지연이 0이라는 뜻은 아니다.
- 최신 입력의 전처리→VE 대기 중앙값 0.11ms, P95 0.46ms. 과거 입력을 큰 queue에 쌓는 방식은 아니다.
- VE 시간 중앙값 211ms는 **2장 묶음의 forward 시간**이다. Stage2 중앙값은 233ms이며, VE와 Stage2의 단순 합은 센서 수신부터의 지연과 다르다.
- 11개 이력의 실제 span은 최소 1.891초/중앙값 1.997초/최대 2.097초. 인접 간격 최대 0.307초, grid offset 최대 0.06293초. 2.4초 이력 및 누락 slot을 포함한 출력은 0개였다.
- 138개 전체 JSONL을 별도로 검사해 서로 다른 LiDAR ID 11개, 증가하는 실제 timestamp, span≤2.12초, 인접 간격≤0.32초, finite waypoint를 확인했다.

차량 정지 상태에서의 실제 센서/네트워크/신경망 검증이다. 손 주행에서의 추종 정확도나 제어 주행 완주를 검증한 것은 아니다. 시험 종료 후 추론 프로세스와 dashboard는 정상 종료했고, MORAI는 종료하지 않았다. 약 0.6초 지연은 여전히 존재하며 10Hz 전체 추론을 달성한 변경은 아니다.

## 설정과 검증

`configs/vldrive_realtime.json`의 runtime:

```json
{
  "encoder_batch_size": 2,
  "encoder_batch_wait_s": 0.22,
  "pin_encoder_inputs": true,
  "encoder_stream_priority": -1,
  "history_max_span_s": 2.12,
  "history_max_adjacent_gap_s": 0.32,
  "history_tolerance_s": 0.07,
  "prediction_hz": null
}
```

11프레임, 목표 입력 간격 0.2초, 모델은 그대로다. **현재 5Hz grid에서 2장씩 묶어 최신 anchor만 발행하므로 정상적인 새 window 공급은 약 2.5Hz이다.** 별도의 prediction sleep 상한을 둔 것은 아니지만 입력 묶음에 따른 빈도 한계는 있다. 이 설정은 현재 MORAI 공유 GPU에서 처리량/지연을 개선하기 위한 선택이며 10Hz 전체 추론을 달성했다는 뜻이 아니다. 더 빠른 GPU에서는 `encoder_batch_size=1`로 묶음 대기를 없애는 비교가 가능하다.

최종 관련 회귀 테스트 **159 passed, 1 skipped (24.29초)**. CPU 테스트 실행에서 CUDA 스트림 테스트 1개는 의도적으로 건너뛰었고 실제 GPU 동작은 위 실측으로 별도 검증했다. 주요 검증은 실제 시각/ID/navigation 보존, 11개 서로 다른 이력, 세대 reset, stale 차단, 과부하 시 bounded queue, batch timeout의 단일 입력 처리, 최신 anchor만 발행, 실제 66ms offset 수용 조건이다. 실제 config의 provenance/load_contract도 GPU 실행에서 통과했다.

실험 전용 코드는 stdin으로 실행했으므로 임시 Python 파일을 남기지 않았다. 수정 기능의 회귀 테스트는 `tests/`에 유지한다. 측정 원본은 `outputs/inference/`, 분석은 이 문서에 보관한다. 기존 사용자 변경 및 모델/학습 소스는 건드리지 않았다.

VLDrive 폴더에서 손 주행 시각화 재실행:

```bash
python inference/realtime_vldrive.py --no-control
```
