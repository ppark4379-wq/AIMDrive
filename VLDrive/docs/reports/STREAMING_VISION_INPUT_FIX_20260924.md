# 연속 VE 입력 처리로 성능 회귀 수정 — 2026-09-24

> 이후 실제 MORAI/GPU 측정에서 한 slot 누락 시 이력을 전부 비우는 조건이 반복 대기를 유발함을 확인했다. 최종 입력 처리와 실제 GPU 검증은 [후속 보고서](INPUT_LATENCY_GPU_FIX_20260925.md)를 따른다. 아래 CPU 모형의 Hz는 실제 GPU 성능이 아니다.

## 원인과 수정

`vldrive_20260924_231402_717620`에서 이전 window 단위 방식은 준비에 약
2.2초가 걸렸다. 과거 이력의 길이도 약 2초이므로 다음 window와 겹치는
프레임이 없어지고, 매번 11개를 새로 인코딩했다. 23:17 관측에서 새 특징
639회에 재사용 2회, 성공 출력 약 0.30Hz였다. raw 수신은 약 8.8Hz로
정상이었다. 계산 시간을 제외한 이전 CPU 모형만으로 검증한 것이 부족했다.

수신 분리는 유지하고 window 전체를 인코딩하는 실행 경로를 제거했다.

```text
UDP 수신 → 가벼운 raw 이력 보관
                    ↓
             고정 0.2초 선택 격자
                    ↓
             CPU 전처리 스레드
                    ↓ 준비된 최신 1개만 보관
             VE 스레드: 한 프레임씩 계산
                    ↓ 최근 연속 11개의 특징 보관
             최신 완성 window 발행
                    ↓
             기존 Stage2 / LLM 추론
```

VE가 현재 프레임을 계산하는 동안 CPU는 다음 프레임을 준비한다.
초기 11개 이후 정상 입력에서는 새 특징 한 개를 추가하고 기존 특징 10개를
재사용한다. LLM이 느리면 최신 완성 window를 가져오며 오래된 window를
순서대로 모두 처리하지 않는다. 원본을 나중에 11개씩 다시 인코딩하지 않는다.

## 시간 선택 기준의 변경

**허용 시간 조건은 이전 구현과 완전히 같지 않다.** 모델 가중치와 11프레임
규격, 목표 0.2초 간격은 유지하지만 다음 두 정책은 구분해야 한다.

| 항목 | 이전 | 이번 수정 |
|---|---|---|
| 선택 기준 | 매번 최신 실제 anchor에서 과거 목표 시각 재계산 | 실행 중 고정된 0.2초 격자 유지 |
| 프레임 허용오차 | 실제 anchor 기준 각 목표에서 ±0.06초 | 각 고정 격자 시각에서 ±0.06초 |
| 실제 anchor 기준 상대 오차 | 최대 0.06초 | 이론상 최대 0.12초 |
| 실제 11프레임 시간 범위 | 약 2초 | 이론상 1.88~2.12초 |

수신 시각은 변경하지 않는다. `stamp`는 실제 원본 수신 완료 시각,
`target_stamp`는 선택 목표 시각이다. 중복 프레임, 보간한 특징,
받지 않은 미래 데이터로 누락된 slot을 채우지 않는다. 선택창이 닫힐 때까지
최대 허용오차만큼 기다린 뒤 원본 시각이 가장 가까운 유효 프레임을 선택한다.

모델은 실제 timestamp를 입력받지 않으므로 이런 시간 간격 변화를 명시적으로
보정할 수는 없다. 이 변경은 수신 jitter를 다루는 추론 정책 변경이며,
주행 정확도가 완전히 동일하다고 검증한 것은 아니다.

제어에 쓰이는 `anchor_received_at`, navigation pose, sim_time은 마지막으로
선택한 실제 센서 snapshot의 값을 유지한다. 격자 시각이나 이후 도착한
전역 navigation으로 대체하지 않는다.

## 지연·누락·자원 처리

- CPU 전처리와 VE 사이 큐는 **최대 1개**다. 밀리면 오래된 대기 작업을 버린다.
- VE 시작 시 실제 센서 나이 제한 0.3초를 검사한다.
- slot이 누락되거나 덮어써지면 특징 이력의 연속성이 끊어진 것으로 표시하고
  연속된 11개를 다시 모은다. 구멍 난 clip을 정상 입력으로 발행하지 않는다.
- reset 전후의 raw·전처리·VE 결과는 generation 검사로 분리한다.
- raw 보관 한도 64개, 특징 이력 11개, 이전 완성 window와 소비 중 참조만 유지한다.
- 모델·센서 전처리 값·현재 velocity=0 recipe·제어기 설정은 바꾸지 않았다.

`target_hz=5`에 해당하는 학습 간격으로 선택 격자를 만든다.
`encoder_max_hz=10`은 VE 시작 속도의 상한이며 실제 10Hz 보장이 아니다.
정상 상태의 선택량은 격자에 따라 초당 약 5프레임이다.
새 경로에서 `capture_hz`는 선택 주기를 바꾸지 않으며 legacy 경로용 설정이다.
보고서에는 실제 `sampling_grid_hz`와 `capture_hz_applies_to`를 따로 기록한다.

**처리량 한계:** VE가 지속적으로 한 장에 0.2초보다 오래 걸리면 초당 5개를
만들 수 없다. 이번 수정은 과거 작업이 쌓이는 것을 막지만 하드웨어 처리량을
만들어 내지는 않는다. 이 경우 큐 drop과 불완전 이력으로 표시한다.
GPU가 느린데 시간 조건을 깨뜨린 11개를 정상 입력처럼 내보내지는 않는다.

## 검증

최종 관련 회귀 **138개 통과(18.69초)**. 실제 실행 config와 선택된
`vldrive_20260921_172411_715080/model-best.pt`의 `load_contract()` 전체 검사도 통과했다.

### 실제 전처리 + 관측 지연을 넣은 CPU 재현

원본 `basic_drive` 첫 lap/episode의 500~507번 장면에서 실제 JPEG와
LiDAR를 읽었다. raw 도착 주기 0.1125초, VE 지연 180ms,
Stage2 지연 274ms로 `run_live()`의 실제 스레드·큐·이력·출력 경로를
14초간 실행했다. VE와 Stage2 모델 계산은 sleep/가짜 출력으로 대체했다.
**실제 GPU·UDP는 사용하지 않았으며 GPU 자원 경쟁을 재현한 측정도 아니다.**

| 항목 | 결과 |
|---|---:|
| 성공 출력 | 43개 |
| 준비 후 출력 빈도 | 약 3.696Hz |
| 새 VE 계산 / 특징 재사용 | 71회 / 600회 |
| 각 발행 window의 새 VE 계산 | 모두 1개 |
| 센서→출력 지연 중앙값 / 최대 | 675ms / 807ms |
| 실제 CPU 전처리 중앙값 / 최대 | 55.6ms / 72.1ms |
| 전처리→VE 큐 대기 중앙값 / 최대 | 0.091ms / 0.262ms |
| slot 누락 / 큐 drop / 이력 gap / stale 폐기 | 모두 0 |
| 격자 기준 최대 시각 오차 | 0.050초 |
| 실제 anchor 기준 최대 상대 오차 | 0.100초 |

종료 시 작업 중 프레임이 있을 수 있어 인코딩 수와 발행 수가 정확히
`+10` 관계로 종료하지는 않는다. 이 결과는 11개 재계산을 제거하고 CPU와
VE 작업을 겹치는 구조의 검사다. **3.696Hz를 실제 GPU 추론 Hz로 인용하면 안 된다.**

### 계산 시간을 포함한 가상시간 회귀

실제 `FrameGrid`와 특징 추가 경로를 사용해 CPU 27ms, VE 165ms,
Stage2 274ms를 독립 worker의 완료 이벤트로 모형화했다.

- 20초에 raw 178개, 전처리 100개, VE 99개, 완성 window 89개,
  후단 출력 64개. 준비 후 출력 약 3.65Hz.
- 평균 센서→출력 624ms, 최대 754ms. 새 특징 한 개 / 재사용 10개.
- VE 300ms 과부하 조건에서는 큐 최대 1개, drop 33회, 이력 gap 32회로
  보고하고 완성되지 않은 clip의 출력은 0개였다. 대기 작업을 계속 쌓거나
  시간이 잘못된 clip을 발행하지 않았다.
- 실제 수신 로그에서도 일부 인접 수신 간격이 0.12초를 넘는다.
  이 경우 격자 ±0.06초 안에 원본이 없어 slot 누락이 생길 수 있다.
  따라서 실제 수신에서 항상 초당 5개의 완성 입력이 나온다고 보장하지 않는다.

회귀 테스트에는 중복 ID 금지, 원본 시각·navigation 보존, 오래된 목표 시각에
가까우면서 실제로는 아직 신선한 sample 선택, 늦은 카메라 재시도,
slot 누락 후 복구, reset, 과부하 큐 한도, 동일 특징 10개 재사용을 포함한다.
실험 전용 스크립트는 stdin으로 실행하고 임시 출력 디렉터리는 종료 시 삭제했다.

## 실행과 확인

이미 실행 중인 Python은 수정 파일을 자동으로 다시 읽지 않는다.
기존 실행을 Ctrl+C로 종료하고 `VLDrive` 폴더에서 다시 시작한다.

```bash
python inference/realtime_vldrive.py --no-control
```

새 경로라면 시작 시 다음 문구가 나온다.

```text
Input: streaming 5Hz sampling grid | 11 cached features | separate preprocessing and VE workers
```

콘솔은 VE 한 장 시간, Stage2 시간, 센서→출력 나이(age)를 분리해서 출력한다.
오래된 완성 입력은 실제 경과 시간과 새 특징 이력 수를 표시하며,
수신 중에도 "새로운 센서 프레임이 없습니다"라고 표시하던 문구를 제거했다.

`inference_report.json`의 주요 항목:

- `input_preparation.encoded_frames` / `feature_cache_hits`: 새 계산과 재사용.
- `sampling_slots_missing`: 격자 시각 허용 범위 안에 실제 프레임이 없었던 수.
- `sampling_slots_expired`: CPU 선택이 늦어 유효한 실제 후보를 구할 수 없던 slot 수.
- `preprocessing_queue_drops`: VE 대기 작업 교체 수.
- `stale_encoder_frames`: VE 시작 전 나이 제한 초과 수.
- `encoded_history_gaps`: 연속된 slot 이력이 끊어진 횟수.

`waypoints.jsonl`에는 `history_timestamps_s`, `history_grid_timestamps_s`,
`history_grid_max_offset_s`, 기존 정의의 `history_max_offset_s`, 실제 span과
최대 인접 간격을 함께 기록한다. `new_vision_frames`는 새 발행 window를
만드는 데 필요한 새 특징 수이며, LLM이 window를 건너뛰면 두 출력 사이에
VE 계산이 여러 번 진행될 수 있다.

이번 작업 중 이전 GPU 추론이 계속 실행 중이었으므로 새 GPU 모델을 중복
실행하지 않았다. 실제 GPU 성능과 주행 품질은 재시작 후 별도 확인 대상이다.
