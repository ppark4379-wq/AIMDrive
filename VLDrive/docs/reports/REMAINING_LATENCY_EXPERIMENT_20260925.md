# 남은 추론 지연 실험 — 2026-09-25

현재 결과: **VE의 동기화 횟수 감소는 전체 지연을 뚜렷하게 줄이지 못했다. 화면 갱신을 5Hz에서 10Hz로 올리는 방법은 표시 대기를 약 60ms 줄였다. Attention 연산 축소는 약 8ms 빨랐지만 waypoint가 완전히 동일하지 않았다.**

이 문서는 운영 반영 전 검토용이다. 운영 소스와 config는 수정하지 않고, 별도 프로세스 안에서만 후보 함수를 교체했다. 차량 제어기 및 제어 UDP 송신은 실행하지 않았다.

## 1. 측정 조건과 범위

- GPU: RTX 5060 Ti 16GB. WSL Ubuntu-20.04의 기존 `lmdrive` 환경, CPU 계산 스레드 2개.
- MORAI 실행 중 측정. 실험 전 GPU 사용률 약 91%, 실험 구간 표본 약 92%, 전력 107–110W, 온도 56–57°C, SM clock 2730MHz. 짧은 표본이므로 전 구간 평균을 뜻하지 않는다.
- Stage 2: `outputs/logs/vldrive_20260921_172411_715080/model-best.pt`, epoch 93, update 10416.
- 체크포인트 SHA-256: `64ae9a84ceef80347be5f00db7cda37c2473082b8880188a2e39822467b77b92`.
- VE: 기존 `outputs/checkpoints/morai_visual_encoder.pth.tar`. 실제 배포와 동일하게 FP32 계산 후 FP16 저장 경계를 재현하고 FP32로 읽었다. Stage 2는 기존 BF16, Gumbel, 11프레임, 약 2초 이력 유지.
- velocity 입력은 이 체크포인트의 기존 계약인 0을 유지했다. 이번 실험에서 속도 입력이나 모델, 학습 loss, instruction 정책을 바꾸지 않았다.
- 모델 로딩·첫 커널 준비 후 비교. 후보 순서를 교대로 바꾸고 동일 입력/seed를 사용했다.

**측정은 두 종류로 구분한다.**

1. 단독 계산 비교: 동일한 실제 녹화 입력을 사용한 VE 16쌍과, 경로 전반 12개 cached window × Gumbel seed 4개 = Stage 2 48쌍.
2. 입력 처리 전체 비교: 실제 녹화 카메라 4개와 LiDAR를 메모리에서 약 8.89Hz로 재생하고, 운영의 CPU 전처리·시간 선택·VE·이력·Stage 2 코드로 처리. 22초씩 `기존 → 후보 → 후보 → 기존` 순서로 실행했다.

두 번째 실험은 UDP 패킷 수신을 녹화 재생으로 대체한 것이다. MORAI의 GPU 부하는 유지했지만 실제 네트워크 지연, 패킷 손실, 이동 중 센서 내용 변화, route navigation 갱신은 평가하지 않았다. PNG 녹화 입력의 CPU 전처리가 실제 UDP JPEG 입력보다 느릴 수 있다. 이전 실시간 측정의 약 594ms와 아래 약 492ms를 직접 비교하여 개선율을 계산하면 안 된다.

녹화 입력: `data/raw/basic_drive/new_structure_full_route_20260917_004823/new_structure_full_route_20260917_004823_lap_001/episode_000`, native association index 500–507을 반복. 이것은 속도 비교 입력이며 주행 정확도 평가 입력은 아니다. 성능 재생에서 instruction은 `Continue straight along the current road.`로 고정했다. 토큰 캐시 wrapper는 비교 양쪽에서 동일하게 제외했으므로 운영과의 작은 CPU 차이는 남는다.

정확도 비교는 2,228개 유효 training window 중 index `0, 202, 404, 607, 809, 1012, 1214, 1417, 1619, 1822, 2024, 2227`을 사용했다. 원래 scene별 navigation 문장과 GT를 사용했고 seed는 `607, 608, 609, 610`이다. 전 데이터셋 성능 평가를 대신하지 않는다.

## 2. VE 동기화 감소

기존 방식의 계산 전/후 stream 대기와 두 번의 finite 확인을 줄였다. 후보는 동일 stream에서 복사·계산·FP16 양자화를 순서대로 수행하고, 양자화 결과의 finite 확인을 한 번 수행했다. NaN/Inf/FP16 overflow 확인은 남겼다. 단독 속도 비교에는 H2D 전송과 결과 확인까지 포함했다.

| VE batch 2 단독 계산 | 기존 | 후보 |
|---|---:|---:|
| 평균 | 173.09ms | 166.10ms |
| 중앙값 | 175.17ms | 159.05ms |
| p95 | 191.51ms | 201.40ms |

평균 절감은 6.99ms이나, 16쌍 차이에 대한 bootstrap 95% 구간은 **−5.16~18.34ms**로 0을 포함한다. 시간 순서의 상관을 완전히 제거한 통계 검정은 아니며, 유의한 개선으로 단정할 수 없다. 오히려 이 표의 p95는 나빠졌다.

특징 차이는 최대 0.001953125. 기존 허용 기준 `atol=0.002, rtol=0.002`를 16쌍 모두 통과했다. 변경 없는 VE 반복에서도 최대 0.0009765625 차이가 있었으므로 CUDA reduction의 기존 수치 변동을 함께 고려해야 한다.

### 입력 처리 전체 결과

| 회차 | 방식 | 출력 수 | 준비 후 출력 Hz | 센서 재생 시점→결과 중앙값 | p95 |
|---|---|---:|---:|---:|---:|
| 1 | 기존 | 49 | 2.502 | 489.5ms | 547.8ms |
| 2 | 동기화 감소 | 49 | 2.506 | 491.8ms | 551.7ms |
| 3 | 동기화 감소 | 49 | 2.498 | 486.8ms | 556.9ms |
| 4 | 기존 | 49 | 2.494 | 494.1ms | 562.5ms |

| 두 회차 통합 | 기존 | 후보 |
|---|---:|---:|
| 평균 지연 | 494.88ms | 491.99ms |
| 중앙값 지연 | 491.54ms | 489.76ms |
| p95 지연 | 560.25ms | 555.91ms |
| 회차별 출력 Hz 평균 | 2.498 | 2.502 |

전체에서는 중앙값 약 **1.8ms, 0.36%** 차이뿐이다. 실행 변동보다 뚜렷한 개선이라는 근거가 부족하다. 네 회차 모두 이력 초기화, 누락 slot, 전처리 큐 drop, 오래된 VE 입력 거절, 시간 범위 위반이 0이었다.

같은 frame/history로 맞춘 49개 출력 비교에서는 기존 반복끼리도, 기존과 후보 사이에도 좌표 최대 차이가 0.0625m였다. 양쪽 모두 waypoint 허용 기준 `atol=0.05m, rtol=0.01`을 통과했다. 일부 token 수는 달라졌으므로 bit-exact라고 표현하지 않는다.

**판정: 운영 반영 우선순위 낮음.** 복잡도를 추가할 만큼의 전체 지연 개선은 확인되지 않았다.

PyTorch 실제 tensor 할당 peak는 네 회차 3.704~3.728GiB였다. allocator 예약량은 같은 프로세스에서 새 CUDA stream으로 회차를 반복하면서 4.758→7.471GiB로 증가했다. 기존 방식인 마지막 회차에서도 증가했으므로 이를 후보만의 메모리 증가라고 해석하지 않는다. 실험 종료 시 해당 프로세스를 종료했다.

## 3. Attention 계산 축소

현재 DDIA는 전체 query/key에 대해 raw QK와 RoPE QK를 모두 계산한 뒤, visual→instruction 블록에만 raw 값을 사용한다. 후보는 RoPE 계산을 유지하고 raw QK는 instruction key 열에 한정했다. mask·RoPE·가중치·선택 방식·precision은 유지했다. GEMM 크기가 바뀌므로 BF16 반올림 결과까지 같다고 가정하지 않았다.

| Stage 2 단독, 48쌍 | 기존 | 후보 |
|---|---:|---:|
| 평균 계산 시간 | 193.98ms | 185.54ms |
| 중앙값 계산 시간 | 195.22ms | 184.92ms |
| p95 | 223.88ms | 215.26ms |
| 표본 GT ADE | 0.22287m | 0.22281m |
| 표본 GT FDE | 0.48033m | 0.47978m |

평균 약 **8.44ms, 4.35%** 절감. 쌍별 차이의 bootstrap 95% 구간은 0.90~16.19ms이다. 이것은 Stage 2 단독 결과이며 전체 지연이 4.35% 줄었다는 뜻은 아니다. 이 후보의 전체 파이프라인 실험은 수행하지 않았다.

48쌍 모두 선택 token 수가 같았고 기존 waypoint 허용 기준을 통과했다. 그러나 좌표 차이는 최대 **0.125m**였다. 이 기준에는 상대 오차 1%가 포함되므로, 허용 기준 통과가 “모든 좌표에서 5cm 이하”를 뜻하지 않는다. 기존 Stage 2를 같은 seed로 두 번 계산한 6쌍은 좌표 차이가 0이었다. 따라서 후보의 좌표 차이를 단순한 Gumbel 재추첨 때문이라고 설명할 수 없다.

표본 ADE/FDE 악화는 관측되지 않았지만, 폐루프 주행 동등성은 검증하지 않았다. **판정: 보류.** 절감 폭이 작고 기존 출력과 완전히 같지 않으므로 바로 적용할 이유가 약하다.

## 4. 화면 갱신 5Hz → 10Hz

운영 HTTP server와 `app.js`를 실제 headless Edge에서 실행했다. 모델 추론 대신 기존 waypoint 결과와 실제 front image를 약 2.5Hz로 재생했다. 화면 갱신만 `5 → 10 → 10 → 5Hz`로 바꿨고, 회차마다 결과 50개를 표시했다. 브라우저 GPU 가속은 끄고 각 GPU 추론 실험이 끝난 뒤 별도로 측정했다.

측정 구간은 **결과 생성 시각 → JS render 이후 첫 requestAnimationFrame callback**이다. 물리 모니터 출력 시각이나 camera JPEG의 onload 완료 시각은 아니다. Windows 로컬 HTTP 경로이므로 실제 WSL→Windows 통신 경로의 추가 지연은 포함하지 않는다. 좌표 변환은 운영 `forward_right` 함수의 원문을 실행했고, Windows에 없는 matplotlib의 관련 없는 그래프 모듈 import만 생략했다.

| 100개 표시/설정 | 5Hz | 10Hz |
|---|---:|---:|
| 평균 표시 대기 | 114.68ms | 54.22ms |
| 중앙값 | 116.75ms | 50.25ms |
| p95 | 201.95ms | 105.31ms |
| 최대 | 217.34ms | 114.71ms |
| 표시 누락 / JS 오류 | 0 / 0 | 0 / 0 |
| server CPU, 코어 1개 기준 | 1.37% | 2.20% |
| renderer main-thread 작업 시간/측정 시간 | 1.24% | 2.21% |
| HTTP 요청/초 | 7.16 | 11.63 |
| 응답 payload/초 | 약 337KB | 약 369KB |

같은 새 image 50개를 두 설정 모두 요청했다. 중복 polling 때문에 camera 전송이 두 배가 되지는 않았다. 전체 browser CPU/GPU 사용률은 별도로 계측하지 않았으며, renderer 수치는 전체 browser CPU 사용률과 다르다.

**판정: 화면 지연 개선용으로 반영 타당.** 평균 약 60.46ms, p95 약 96.64ms 감소했고 이 실험 범위의 추가 CPU/통신량은 작았다. 바꿀 항목은 `configs/vldrive_realtime.json`의 `visualization.refresh_hz: 5 → 10`이다. 현재 config에는 아직 반영하지 않았다. 모델의 추론 Hz와 차량 제어 응답 시간에는 직접적인 개선이 없다.

## 5. 남은 지연의 의미

기존 방식의 재생 결과 평균 약 495ms는 다음 항목을 포함한다.

- 최신 프레임 CPU 전처리 약 52ms.
- 두 프레임 VE 계산 약 169ms.
- 11프레임 Stage 2 계산 약 187ms.
- 위 세 항목을 뺀 약 87ms는 시간 slot 선택·입력 준비·복사·대기·후처리 등이 섞인 잔여 시간이다. 세부 항목별로 직접 계측한 결과는 아니다.

전처리 완료 후 VE 큐 대기 평균은 약 0.12ms였다. 이 실험에서는 처리할 입력이 큐에 길게 쌓이는 문제는 보이지 않았다. UI의 약 115ms 표시는 위 약 495ms와 별개이며 서로 다른 실험의 평균을 단순 합산하여 실시간 지연이라고 주장할 수 없다.

현재 입력 선택은 5Hz이고 VE가 두 프레임을 한 번에 처리한 뒤 마지막 프레임에서만 window를 publish한다. 따라서 안정적인 batch 2 구간의 새 예측은 약 **2.5Hz**이다. `prediction_hz: null`이어도 이 공급 주기는 남는다. 이 대기에는 계산 자원을 아끼는 목적이 있으며 “GPU만 교체하면 자동으로 10Hz”가 되는 구조는 아니다.

batch 1 전환은 별도 후보가 될 수 있다. 하지만 VE/LLM 실행 횟수 증가로 다시 경합·입력 누락이 생길 수 있다. 이번 비교에서는 이 설정을 바꾸지 않았고 성공을 주장하지 않는다. 과거 visual KV를 그대로 재사용하는 방법 역시 Gumbel·MEFA로 이력 token이 바뀌므로 이번에 적용하지 않았다.

**하드웨어 영향:** MORAI가 같은 GPU를 사용하는 상황에서 높은 부하가 관측됐다. 종료 확인을 받지 못해 OFF 비교는 수행하지 않았다. 따라서 MORAI가 몇 ms를 더하는지, 별도 PC에서 몇 Hz가 되는지는 이번 결과로 확정할 수 없다. 시뮬레이터는 임의로 종료하지 않았다.

## 6. 정리 및 정리 작업 상태

사용자에게 제안할 즉시 후보는 화면 갱신 10Hz이다. VE 동기화 변경은 우선순위를 낮추고, attention 축소는 수치 동등성·폐루프 검증이 더 필요해 보류한다. 운영 반영은 사용자의 검토 뒤에 진행한다.

운영 소스·config 227개 파일의 실험 전후 SHA-256을 비교하여 모두 동일함을 확인했다. 기존 사용자의 미커밋 변경은 보존했다. 비교한 경로→SHA 목록의 정렬 JSON digest는 `a8bbcbd62691bfc2fefbf422cfbbba726824b1ed7ebf09f76f1ed034b9e3f22a`이다.

GPU 벤치마크와 임시 Edge 실행은 정상 종료했다. `.runtime/latency_experiment_20260925` 아래 실험 코드·임시 측정 파일 18개를 삭제하고 폴더가 남지 않았음을 확인했다. 이번 작업에서 새로 남긴 파일은 이 Markdown 보고서뿐이다.
